# User Interface (UI)

## Purpose

Hesiva Version 1 provides a fast, reliable, keyboard-friendly desktop interface for a
large-animal veterinarian's customer account workflow. It should preserve the speed and
familiarity of the legacy application while making financial history clearer and safer to use.

Hesiva is an account and balance tracking application. It is not a clinic-management or medical
record system.

---

# Version 1 UI Freeze and Visual Reference

The Hesiva Version 1 UI is visually frozen.

[`docs/design/V1UIFreeze.pdf`](design/V1UIFreeze.pdf) is the authoritative visual implementation
reference for Version 1. UI implementation must follow its visual structure, layouts, visible
labels, interaction patterns, component appearance, empty states, dialogs, density, and overall
design language unless an established business or technical constraint requires otherwise.

The PDF was produced under the former working product name **Cari**. Product-name text shown in the
frozen artifact must be implemented as **Hesiva**; its visual layout and structure remain
authoritative.

The remaining project documentation stays authoritative for business rules, database semantics,
security, persistence, backup and restore safety, legacy import behavior, architecture, and scope.
When a visual detail could imply behavior that conflicts with those rules, the implementation must
preserve the documented rule while remaining as visually faithful to the PDF as possible.

Visual deviations during implementation must be intentional, justified, and documented. They must
not be invented ad hoc.

# Design Principles

The frozen interface uses a classic, dense desktop application language:

- Linux-first, with Windows as a secondary supported platform
- Mouse-friendly and keyboard-first where practical
- Fast access to common customer, transaction, and payment actions
- High information density with simple, predictable layouts
- A restrained light theme without decorative dashboard treatment
- Restrained blue for primary actions
- Neutral treatment for secondary actions
- Red for destructive or void actions
- Amber for archive and warning actions where shown
- Clear focused and invalid input states
- Compact tables with strong selected-row states
- Right-aligned financial values
- Compact, informative empty states
- Reusable information, warning, error, and success presentation patterns
- No unnecessary animation or mobile-style navigation

The PDF, rather than this document, remains authoritative for exact visual proportions, spacing,
and component styling. Implementation should not introduce unrelated pixel-level styling rules.

## Terminology

The Turkish Version 1 interface uses these terms consistently:

- **Müşteri**
- **İşlem**
- **Ödeme**
- **Borç**
- **Bakiye**
- **Güncel Bakiye**
- **Son İşlem**
- **Hayvan**
- **Hatırlatma**
- **Hesap Hareketleri**
- **Hesap Özeti**
- **Aylık Özet**
- **Yıllık Özet**

Financial tables use **Borç** and **Ödeme** as the ordinary user-facing column labels.

**Son İşlem** means the customer's most recent non-void financial transaction. It is calculated
from transaction history and does not represent a separate physical or medical visit.

Customer balance presentation follows one rule throughout the interface:

- A positive balance is shown as its amount with **Borç**.
- Zero is shown neutrally, for example **0,00 TL**.
- A negative balance is shown without a minus sign, using its absolute amount with **Fazla Ödeme**.

The underlying balance remains signed integer kuruş. **Alacak** is not the ordinary user-facing
label for a negative balance.

# Window and Resize Behavior

The 1366×768 target is the primary minimum design reference, not a fixed window size.

- `MainWindow` is resizable.
- Larger displays show more useful content instead of proportionally scaling the whole interface.
- Fonts and controls do not proportionally scale with window size.
- The left customer pane has a sensible minimum width so names, balances, and dates remain useful.
- The right detail pane receives most additional horizontal space.
- Tables expand intelligently, especially descriptive columns.
- Additional vertical space displays more rows.
- Dialogs remain compact unless extra size provides genuinely useful content.
- The desktop navigation structure does not transform into a mobile or responsive navigation mode.
- Layouts and splitters should govern sizing; fixed absolute coordinates should not define the
  resizable application layout.

The main interface must remain fully usable at 1366×768 and make good use of Full HD and larger
displays.

# Main Window

The frozen main window has a traditional desktop structure.

## Top Area

The top area contains:

- Application title bar
- Traditional menu bar, including the frozen **Dosya**, **İşlemler**, **Rapor**, **Ayarlar**, and
  **Yardım** placement
- Customer search
- Sorting selector

Search updates the visible customer results promptly. Sorting follows the available Version 1
customer criteria, including name, balance, last activity, and registration/creation date where
offered.

The frozen sort options use these deterministic Version 1 rules:

- **En Yüksek Borç** — raw signed active balance descending, then full name and customer ID
  ascending. Positive debt comes before zero; negative **Fazla Ödeme** balances come last.
- **Ada Göre** — full name and customer ID ascending using the existing database ordering.
- **Son İşlem** — latest non-void transaction date descending, transaction time descending with
  missing times last, then full name and customer ID ascending. Customers without an active
  transaction come last.
- **Kayıt Tarihi** — `registered_on` descending with missing dates last, then full name and customer
  ID ascending. It does not fall back to the technical creation timestamp.

The interface does not display server, network, user-role, or administrator status concepts.

## Main Body

The main body is split into:

- A left customer list pane
- A right selected-customer detail pane

The left pane lists active customers and shows, for each row:

- Customer name
- Balance
- **Son: DD.MM.YYYY** using the most recent non-void transaction date

It also includes:

- Visible customer/result count
- **Yeni Müşteri** action

The right pane header shows the selected customer's:

- Name
- Phone
- **Son İşlem**
- **Güncel Bakiye**

Below it are the frozen tabs:

- **Genel**
- **Hayvanlar**
- **Hesap Hareketleri**
- **Hatırlatmalar**

When no customer is selected, the right pane shows an explicit compact message such as
**Detayları görüntülemek için bir müşteri seçin.** It must not display stale details from a previous
selection.

The bottom status area uses restrained information such as **Hazır**, relevant record counts, and
the Version 1 version label where appropriate. It does not expose the production database filename
as ordinary status information.

# Customers

## New and Edit Customer Dialogs

Both dialogs use the same compact field structure:

- **Ad Soyad** — required
- **Telefon** — optional
- **Adres** — optional
- **Notlar** — optional

The normal UI does not expose database or migration metadata:

- Database ID
- Legacy reference ID
- Creation timestamp
- Update timestamp
- Archive timestamp

Duplicate customer names are allowed. Validation must not visually imply that names are unique.

## General Tab

The **Genel** tab presents:

- Phone
- Address
- Registration date
- **Son İşlem**
- Total debt
- Total payment
- **Güncel Bakiye**
- Notes
- Customer edit action
- Customer archive action

Displayed totals and balances are derived from non-void transaction history. No editable or stored
balance is presented as authoritative.

## Customer Archive and Unarchive

The archive action requires an explicit confirmation that explains:

- The customer will leave the active list.
- Customer history, animals, reminders, and account movements will be preserved.
- The action is an archive operation, not physical deletion.

An archived customer must not be described as deleted.

Version 1 provides access to archived customers and an **Arşivden Çıkar** action. Unarchiving sets
the customer back to active without changing transactions, reminders, or animal archive states.
Unarchiving an already active customer has no additional effect.

# Transactions and Payments

## New Transaction Dialog

**Yeni İşlem** is a compact, keyboard-oriented dialog containing:

- **Müşteri** — selected, read-only context
- **Tarih** — required and given an appropriate editable default
- **Açıklama** — required unrestricted free text
- **Tutar** — required and initially blank
- **Hayvan** — optional, limited to eligible animals belonging to the selected customer
- **Notlar** — optional

The description is not tied to a product, service catalog, inventory item, treatment record, or
predefined list. The user can enter any meaningful account description.

The ordinary debt-entry UI accepts a positive magnitude. The service layer validates and stores the
signed integer-kuruş movement according to the documented transaction rules.

There is no normal physical-delete operation and no ordinary transaction-edit action in Version 1.
To correct an error, the user voids the incorrect transaction and creates a new correct transaction
when required. The original movement remains stored in history.

## Receive Payment Dialog

The dedicated **Ödeme Al** dialog contains:

- **Müşteri** — selected, read-only context
- **Tarih** — required
- **Tutar** — required and initially blank
- **Açıklama** — normally starts as **Tahsilat** and remains editable

It also shows:

- **Mevcut Bakiye**
- **Ödeme Sonrası Bakiye**

The user enters a positive payment magnitude. The service layer converts it exactly once to a
negative signed financial movement. Payment is account-level and is not allocated to a specific
earlier debt.

Overpayment is allowed. A resulting negative signed balance is customer credit and must not be
presented as an input error. Its visible amount follows the **Fazla Ödeme** presentation rule above.

## Account History Tab

The frozen **Hesap Hareketleri** table presents these visible concepts:

- **Tarih**
- **Saat**
- **Açıklama**
- **Hayvan**
- **Borç**
- **Ödeme**
- **Bakiye**

Money is right aligned. Rows and selected-row states remain compact and easy to scan. The running
balance display must be based on the same signed, non-void history rules as the authoritative
balance calculation.

Available actions include:

- **Yeni İşlem**
- **Ödeme Al**
- **Yazdır**, where applicable
- **İşlemi İptal Et** for a selected active transaction

Voided transactions:

- Remain in history
- Are visibly marked as voided or cancelled
- No longer affect active balance, last activity, or normal report totals
- Cannot be physically removed through the normal interface

Voiding requires a clear confirmation. An optional void reason may be entered for audit or context;
the UI must not claim that a reason is required.

If no transactions exist, the tab displays a compact empty state rather than an empty, unexplained
table.

# Animals

The **Hayvanlar** tab uses a compact list with the frozen visible columns:

- **Küpe No**
- **Ad**
- **Tür**
- **Not**

The add and edit dialogs contain:

- **Küpe No** — optional
- **Ad** — optional
- **Tür** — optional
- **Notlar** — optional

**Tür** is a free-text model field. The UI may use an editable combo box with common suggestions,
but the user must be able to enter a value outside those suggestions. It is not a fixed enum.

Archiving an animal removes it from the active list while preserving every historical financial
reference. The archive confirmation says this explicitly. No physical-delete language is used.

Version 1 provides access to archived animals and an **Arşivden Çıkar** action. An animal can be
unarchived only while its owning customer is active. The UI must not automatically unarchive the
customer or cascade animal unarchive when a customer is unarchived.

Version 1 animal screens do not add breed, sex, birth date, diagnosis, treatment records,
vaccination history, or a medical timeline.

# Reminders

The **Hatırlatmalar** tab defaults to active reminders and displays:

- **Tarih**
- **Hatırlatma Notu**
- **Durum**

Available actions are:

- **Hatırlatma Ekle**
- **Tamamlandı**
- **Düzenle**
- **İptal Et**

An optional **Tamamlanmışları Göster** control exposes completed history without mixing it into the
default active list.

The reminder dialog requires:

- **Tarih**
- **Not**

Reminder presentation distinguishes active, completed, cancelled, and overdue states. Completion
and cancellation preserve the reminder record and prevent it from appearing in the active due list.
The UI uses reminder terminology and does not represent these records as financial transactions or
as a separate appointment-management system.

# Reports and Statements

## Customer Account Statement

The frozen **Hesap Özeti / Ekstre** screen contains:

- Customer details
- Date-range filter
- Debt/payment rows
- Debt and payment totals for the visible reporting period
- **Güncel Bakiye**
- **Yazdır**
- **PDF Olarak Kaydet**

The date filter controls the visible rows and period-report data. **Güncel Bakiye** means the
customer's overall current balance from all active transaction history; it is not silently redefined
as the net movement in the selected period. If a period-end balance is ever shown, it must be
separately and unambiguously labeled.

Payments in a period must not be described as paying debts created in that same period because
Version 1 does not allocate payments to individual debt movements.

## Monthly Summary

**Aylık Özet** provides:

- Year
- Month
- **Oluşan Borç**
- **Alınan Ödeme**
- **Net Hareket**
- **Yazdır**
- **PDF Olarak Kaydet**
- A restrained debt/payment comparison visualization if implemented

## Yearly Summary

**Yıllık Özet** provides:

- Year
- Annual debt, payment, and net movement values
- Monthly breakdown
- **Yazdır**
- **PDF Olarak Kaydet**
- A restrained visualization if implemented

Reports do not add customer rankings, CRM metrics, or unrelated dashboard KPIs.

# Backup and Restore

The UI describes and coordinates backup and restore; the safety and implementation rules remain
authoritative in [`docs/07-backup.md`](07-backup.md).

## Backup Screen

The frozen **Yedekleme ve Veri Güvenliği** screen visibly includes:

- Backup destination
- Last successful backup
- Backup failure status when relevant
- **Konumu Değiştir**
- **Geri Yükle**
- **Yedek Oluştur**

It recommends a different physical device where available and accurately distinguishes a local
same-disk fallback from hardware-failure protection.

## Restore Screen

The restore confirmation visibly includes:

- Backup date
- Application version
- Database version
- A strong warning that current data will be replaced
- Cancel and restore actions

The workflow must not imply that replacement begins before validation and the required safety
backup. Low-level snapshot, verification, and atomic replacement details belong in the backup
documentation rather than the primary UI.

# Legacy Import

The frozen **Eski Verileri İçe Aktar** wizard follows five stages:

1. **Kaynak**
2. **Analiz**
3. **Onay**
4. **Aktarım**
5. **Sonuç**

The source step shows:

- A Veresiye 5 `.exa` backup as the primary source
- An optional, advanced `.edb` source

The UI must state that the source is read-only and that the original backup is not changed or
deleted.

The remaining stages show:

- Discovered customer and account-movement counts, date range, and warnings during analysis
- A clear import summary before confirmation
- Meaningful progress stages for customers, financial movements, and verification
- Success counts and warnings in the result
- A user-friendly failure result

Technical details are available through the import report or details action rather than raw
implementation errors on the primary screen. Warnings are not silently hidden.

Import behavior follows [`docs/08-import.md`](08-import.md): the destination is an empty Hesiva
business database, the original source remains unchanged, ambiguous source rows are not guessed,
and critical failure leaves no partial production import. The UI does not invent default values or
claim that arbitrary financial movements may simply be skipped.

# Authentication and First Run

## First Password Creation

On first launch, Hesiva asks the user to create and confirm one local application password. The
compact dialog provides clear validation, including a mismatch message, and does not introduce a
username, email address, cloud account, or user-role concept.

## Login

Normal login asks only for the local password, presents an understandable error after failure, and
allows entry after successful authentication. Version 1 remains unlocked until the application is
closed.

The UI must not imply that the application password encrypts the SQLite database. Password storage
and authentication behavior remain governed by [`docs/06-security.md`](06-security.md).

## Initial Start Choice

The frozen initial choice uses:

- **Boş Veritabanıyla Başla**
- **Eski Veresiye 5 Verilerini İçe Aktar**

It does not add account, tenant, server, or cloud setup.

## Change Password

The compact password-change dialog contains:

- Current password
- New password
- New-password confirmation
- Cancel and change-password actions

It reports success or validation failure in the standard user-facing patterns.

# Empty, Error, and Confirmation States

## Empty States

The frozen reusable empty-state language covers:

- No customers
- No selected customer
- No transactions
- No animals
- No reminders
- No search results

Each state briefly explains what is absent. A primary action appears only when it helps the user
continue, such as **Yeni Müşteri** for an empty customer list.

## Errors and Feedback

Errors are understandable and action-oriented. Normal UI surfaces must not expose:

- Python tracebacks
- SQL
- Stack traces
- Raw SQLite or Alembic details
- Implementation-specific exception messages

Technical details may be recorded safely or made available through an appropriate report without
placing sensitive customer or financial data in logs.

Information, warning, error, and success messages reuse the frozen component patterns and colors.

## Confirmations

Confirmation dialogs state the actual operation and its consequences:

- Archive removes a customer or animal from the active list while preserving history.
- Void/cancel preserves the historical record and changes its active effect or lifecycle state.
- Restore is a destructive replacement workflow protected by the backup rules.

The interface must not use a generic delete label when the operation is archive, void, or cancel.
Destructive actions are never the default result of an accidental Enter key press.

---

# Keyboard Interaction

Common dialogs follow a predictable keyboard sequence:

- **Tab** → next field
- **Shift+Tab** → previous field
- **Enter** → save or confirm only when validation succeeds and the action is safe
- **Esc** → cancel or close

Initial focus should support the shortest safe workflow, such as focusing **Açıklama** when a new
transaction already has an appropriate date default.

Enter must not trigger archive, void, restore, or another destructive action merely because that
button has focus by default. Only context-specific function-key shortcuts already represented in
the frozen PDF are in Version 1 scope; implementation must not invent a larger shortcut system.

The Version 1 UI does not include:

- Inventory management
- Product or service catalog
- Medical records
- Diagnosis or treatment history
- Vaccination management
- Appointment scheduler
- Cloud synchronization
- Multi-user roles
- Network server status
- CRM analytics
- Customer rankings
- ERP features
- Mobile or responsive-navigation layouts
- Decorative dashboards
- Advanced analytics

Future possibilities must not influence or complicate the frozen Version 1 interface without an
explicitly approved scope and documentation change.

# Summary

Hesiva Version 1 uses a frozen, dense, conventional desktop interface centered on a customer list and
selected-customer details. Common account tasks remain visible, fast, keyboard-friendly, and
traceable. The PDF defines what the interface looks like; the project documentation defines what
its operations mean and how they preserve business data.
