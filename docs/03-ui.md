# User Interface (UI)

## Purpose

The user interface is designed for a large-animal veterinarian who performs the same account-tracking tasks repeatedly during daily work.

The primary goal is not to create a visually impressive application. The goal is to create a professional desktop application that is fast, reliable, easy to learn, keyboard-friendly, and comfortable to use for many years.

The UI should preserve the familiar workflow of the legacy application while modernizing its appearance and improving clarity.

---

# Design Principles

The interface follows these principles:

- Linux-first desktop application
- Windows supported as a secondary platform
- Mouse and keyboard friendly
- Keyboard-first workflow whenever practical
- Minimal clicks
- Minimal mouse movement
- High information density
- Simple and predictable layouts
- Large, readable typography
- Professional business appearance
- No unnecessary animations
- No decorative dashboard design
- No mobile-style navigation
- Conservative, long-term visual design

The software should feel like a natural replacement for the legacy application rather than an unrelated product.

---

# Visual Style

The interface should use a clean desktop design.

Recommended characteristics:

- Light theme for Version 1
- Neutral colors
- Limited use of accent colors
- Red primarily for warnings, overdue reminders, and destructive/void actions
- Green primarily for successful operations
- Clear table layouts
- Consistent spacing
- Rounded corners only where appropriate
- System or widely available readable fonts

Information density and readability take priority over decorative effects.

---

# Login Window

The application opens with a password screen.

Features:

- Password field
- Login button
- Minimal interface
- Clear error message after an incorrect password

The first launch asks the user to create and confirm a password.

After successful authentication, Version 1 remains unlocked until the application is closed.

---

# Main Window

The main window is divided into two primary sections.

## Left Panel

Contains:

- Customer search
- Sorting options
- Filter options
- Customer list

Each customer row displays:

- Customer name
- Current balance
- Last activity date
- Reminder indicator when relevant

"Last activity" means the most recent non-voided financial transaction date.

The Turkish UI should use a term such as **Son işlem** rather than implying that the application stores a separate medical visit record.

The customer list should support instant searching.

Useful sorting options include:

- Name
- Highest balance/debt
- Lowest balance/debt
- Most recent activity

---

## Right Panel

Displays information about the selected customer.

Header:

- Customer name
- Phone number
- Current balance
- Last activity

Below the header are four tabs:

- General
- Animals
- Account History
- Reminders

---

# General Tab

Displays customer information.

Contains:

- Name
- Phone
- Address
- Notes
- Registration date
- Last activity
- Total debt
- Total payments
- Current balance

The displayed balance is always calculated from active transaction history.

---

# Animals Tab

Displays animals belonging to the selected customer.

Each animal may contain:

- Ear tag number
- Name (optional)
- Species (optional)
- Notes (optional)

Animals are optional.

A customer may have zero, one, or many animals.

This is not a medical record system.

Animals that are no longer active should be archived rather than physically deleted when history references them.

---

# Account History Tab

This is one of the most frequently used screens.

It displays all financial movements in chronological order.

Each active transaction contains at minimum:

- Date
- Description
- Amount

An optional animal and note may also be visible through row details or editing.

Examples of free-text descriptions include:

- Birth + Medicine
- Examination
- Treatment
- Feed
- Needles
- Serum
- Artificial Insemination
- Travel
- Any custom description

Descriptions are always unrestricted free text.

Version 1 does not require a catalog and does not require description suggestions.

Buttons:

- New Transaction
- Receive Payment
- Account Statement / Print

Editing and voiding a transaction should be available without making the main workflow cluttered.

Voiding requires confirmation and does not physically remove the historical record.

Transactions should be easy to scan and may be grouped by date where appropriate.

---

# Reminders Tab

Displays reminders belonging to the selected customer.

Each reminder contains:

- Reminder date
- Description
- Status

Due and overdue reminders should be visually clear.

Users should be able to:

- Create reminder
- Edit reminder
- Mark reminder completed

Completed reminders remain stored but should not appear as active due reminders.

---

# New Transaction Dialog

Modal dialog.

Fields:

- Customer (read only)
- Date
- Description
- Amount
- Animal (optional)
- Notes (optional)

Behavior:

- Date defaults to today but remains editable.
- Description is unrestricted free text.
- Amount starts empty rather than forcing a default value.
- Animal selection only contains animals belonging to the selected customer.
- Initial keyboard focus should normally move to Description because Date already defaults to today.

Buttons:

- Cancel
- Save

Keyboard behavior:

- Enter → Save when validation succeeds
- Esc → Cancel
- Tab → Next field
- Shift + Tab → Previous field

Validation:

- Description cannot be empty.
- Amount must be greater than zero in the debt-entry UI.

The dialog should be completable quickly without requiring the mouse.

---

# Receive Payment Dialog

Displays:

- Customer
- Current balance
- Payment amount
- Date
- Notes

Behavior:

- Date defaults to today but remains editable.
- The user enters a normal positive payment amount.
- The service layer stores the resulting financial movement as a negative amount.
- A payment is not allocated to a specific previous debt.
- Payments greater than the current positive balance are allowed; the resulting negative balance represents customer credit.

Buttons:

- Cancel
- Save

---

# New Customer Dialog

Contains:

- Name
- Phone
- Address
- Notes

The dialog should remain intentionally simple.

Advanced business/accounting identity fields are not required for Version 1.

---

# Add Animal Dialog

Contains:

- Ear tag number
- Name (optional)
- Species (optional)
- Notes

Animals can be added, edited, or archived.

The UI must not allow a transaction for one customer to reference another customer's animal.

---

# Reports

Version 1 must support printable customer account statements.

Customer statements include:

- Customer information
- Transaction history
- Total debt
- Total payments
- Current balance

Statements should be printable and exportable as PDF.

Version 1 also includes basic monthly and yearly financial summaries.

These summaries may show:

- Debt created during the selected period
- Payments received during the selected period
- Net movement
- Outstanding balances where appropriate

The UI must not describe payments received in a period as payments of debt created in that same period because Version 1 does not allocate payments to individual debts.

---

# Advanced Statistics

Advanced analytics are outside the Version 1 scope.

Possible future features include:

- Additional comparisons
- Trend charts
- Custom dashboards
- Saved report presets
- Deeper analytics

Basic monthly and yearly financial summaries remain part of Version 1.

---

# Accessibility

The interface should remain usable on:

- 1366×768 displays
- Full HD displays
- Multi-monitor setups

The application must remain fully usable without requiring a high-resolution display.

---

# Performance

The interface should feel immediate during normal work.

Requirements:

- Fast startup
- Fast customer search
- Immediate table updates after successful writes
- No noticeable delays during normal customer/transaction workflows

Long-running import, restore, backup, or report operations should display progress when they may take noticeable time.

Smooth workflow is more important than visual effects.

---

# Future UI Improvements

Possible post-Version-1 improvements include:

- Dark mode
- Saved filters
- Custom table layouts
- Recently used description suggestions
- Additional reports
- Advanced statistics

These features must not complicate Version 1.

---

# Summary

The UI is designed around one principle:

The veterinarian should be able to perform common daily account-tracking tasks at least as quickly as in the legacy software while requiring minimal retraining.

The interface should preserve the speed and familiarity of the old workflow while making the application easier to read, safer, and more maintainable.
